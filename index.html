1. Intro to Server-Side & HTTP Architecture

Day 01
  • Client-Server Model: Client (Presentation/UI ส่ง Request) ⇄ Server (Business Logic, Auth, Database ประมวลผลและตอบกลับ Response)
  • SSR vs CSR: SSR (Server-Side Rendering) Server สร้าง HTML สำเร็จรูป เหมาะกับ SEO & Fast First Paint / CSR (Client-Side Rendering) Browser โหลด JS เปล่าแล้ว Render เอง เหมาะกับ Rich App (SPA)
  • HTTP Protocol & REST: Stateless Protocol อาศัย JWT/Session/Cookie • Methods: GET (Read), POST (Create - 201), PUT/PATCH (Update), DELETE (Delete)

2. Git Architecture & Version Control

Day 02 • Git
  • 4 Git States: Working Directory ➔ git add ➔ Staging Area (Index) ➔ git commit ➔ Local Repo ➔ git push ➔ Remote Repo
  • Branching & Switching: git branch <name>, git checkout -b <name> หรือ git switch -c <name>
  • Merge & Conflict Resolution: git merge <branch> หากเกิดข้อขัดแย้ง ให้เปิดไฟล์แก้จุด <<<<<<< HEAD แล้วสั่ง git add . และ git commit
  • .gitignore Essentials: ต้องใส่ node_modules/, .env, *.log เสมอเพื่อความปลอดภัย

3. Docker & Containerization Infrastructure

Day 02 • Docker
  • VM vs Container: VM ต้องมี Guest OS ทุกตัว (หนัก/ช้า) ส่วน Container แชร์ Host OS Kernel ผ่าน Namespaces (แยก PID, NET, MNT) และ cgroups (จำกัด CPU/RAM)
  • Dockerfile Layer Caching: วาง COPY package*.json ./ และ RUN npm install ก่อน COPY . . เพื่อไม่ต้องติดตั้ง dependencies ซ้ำเมื่อแก้โค้ด
  • Port Mapping & Named Volumes: -p HOST:CONTAINER (เช่น 3307:3306 หรือ 27017:27017) และ volumes: [mongo_data:/data/db] เพื่อรักษาข้อมูลไม่ให้สูญหาย

4. Node.js Core Modules & Asynchronous Flow

Day 04
  • V8 Engine & Event-Driven: Single-threaded Event Loop แบบ Non-blocking I/O รองรับ Request ปริมาณมากพร้อมกันได้อย่างมีประสิทธิภาพ
  • Async/Await vs Promise vs Callback: ใช้ async/await คู่กับ try...catch เพื่อให้อ่านเข้าใจง่ายและจัดการ Error ได้รอบด้าน
  • Core Modules: fs (readFile/writeFile), path (path.join/resolve ป้องกัน path issue ข้าม OS), os (os.platform, os.freemem), http (http.createServer)
  • CommonJS vs ESM: CommonJS ใช้ require() และ module.exports (โหลด Synchronous เหมาะกับ Backend Node.js)

5. Express Middleware, Router & Error Pipeline

Day 04 • Day 06
  • Middleware Sequence & next(): ฟังก์ชันที่เข้าถึง (req, res, next) หากไม่ส่ง Response ต้องเรียก next() เสมอ มิฉะนั้น Request จะค้าง (Hang)
  • Built-in & Third-party: app.use(express.json()) (แยก Parse Body ก่อน Routes) และ app.use(cors())
  • Express Router: แยก Router ออกเป็นโมดูล เช่น routes/studentRoutes.js แล้วนำมา mount ด้วย app.use('/api/students', studentRouter)
  • Global Error Handler: ฟังก์ชัน 4 พารามิเตอร์ (err, req, res, next) วางไว้บรรทัดล่างสุดเพื่อดักจับ Error ทุกรูปแบบ

6. MySQL, Prepared Statements & Soft Delete

Day 06 • MySQL
  • Connection Pool: ใช้ mysql2/promise ผ่าน mysql.createPool() เพื่อ reuse connection รองรับ concurrent users
  • SQL Injection Prevention: ใช้ Parameterized Query (? placeholders) เช่น SELECT * FROM users WHERE email = ? ห้ามต่อ String เด็ดขาด!
  • Soft Delete Pattern: ห้าม DELETE FROM แต่ใช้ UPDATE users SET deleted_at = NOW() WHERE email = ? AND deleted_at IS NULL และ Query ดึงเฉพาะ WHERE deleted_at IS NULL

7. MongoDB & Mongoose ODM (Exam Core)

Day 06 • MongoDB
  • Connecting: mongoose.connect(process.env.MONGO_URI) ในไฟล์ config/db.js
  • Schema & Validations: required, unique, min, max, enum, trim, default, และ { timestamps: true }
  • CRUD Methods: Model.create(), Model.find(filter), Model.findById(id), Model.findByIdAndUpdate(id, body, { new: true, runValidators: true }), Model.findByIdAndDelete(id)
  • Duplicate Key Trap: ดักจับ err.code === 11000 แล้วคืนค่า 400 Bad Request

8. SQL Joins, Constraints, Views & Prisma ORM

Day 07
  • SQL Joins: INNER JOIN (เฉพาะแถวที่ Match กันทั้ง 2 ตาราง), LEFT JOIN (เอาทุกแถวฝั่งซ้าย ถ้าขวาไม่มีเป็น NULL), RIGHT JOIN, FULL JOIN (MySQL ใช้ UNION เชื่อม LEFT + RIGHT), SELF JOIN (เชื่อมตารางตัวเอง)
  • Constraints & Logic: PRIMARY KEY, FOREIGN KEY (รักษา Referential Integrity), EXISTS Operator สำหรับ Correlated Subquery, CASE WHEN ... THEN ... ELSE ... END
  • Views & Prisma ORM: CREATE VIEW เป็น Virtual Table เก็บ Query Logic • Prisma ORM กำหนด Model ใน schema.prisma และเรียกใช้งานผ่าน prisma.user.findMany(), prisma.user.create()

const studentSchema = new mongoose.Schema({
  studentId: {
    type: String,
    required: [true, 'Student ID is required'],
    unique: true,
    trim: true
  },
  name: {
    type: String,
    required: [true, 'Student name is required'],
    trim: true
  },
  major: {
    type: String,
    required: true,
    enum: ['IT', 'CS', 'DS', 'SE'],
    default: 'IT'
  },
  gpa: {
    type: Number,
    min: [0.0, 'GPA cannot be less than 0.0'],
    max: [4.0, 'GPA cannot be more than 4.0'],
    default: 0.0
  },
  isActive: {
    type: Boolean,
    default: true
  }
}, {
  timestamps: true // สร้าง createdAt และ updatedAt อัตโนมัติ
});

module.exports = mongoose.model('Student', studentSchema);

require('dotenv').config();
const express = require('express');
const cors = require('cors');
const connectDB = require('./config/db');
const studentRoutes = require('./routes/studentRoutes');

const app = express();
const PORT = process.env.PORT || 5000;

// 1. เชื่อมต่อฐานข้อมูล MongoDB
connectDB();

// 2. Built-in Middleware (สำคัญมาก! ต้องวางก่อน Route Handler)
app.use(cors());
app.use(express.json());

// 3. Root Healthcheck Route
app.get('/', (req, res) => {
  res.status(200).json({ message: 'Server-Side Practical Exam API is running!' });
});

// 4. Mount API Routes
app.use('/api/students', studentRoutes);

// 5. 404 Route Not Found Middleware
app.use((req, res, next) => {
  res.status(404).json({ error: `Route ${req.originalUrl} not found` });
});

// 6. Global 500 Error Handling Middleware (ต้องมีครบ 4 parameters เสมอ)
app.use((err, req, res, next) => {
  console.error('Unhandled Error:', err.stack);
  res.status(err.status || 500).json({
    error: err.message || 'Internal Server Error'
  });
});

app.listen(PORT, () => {
  console.log(`🚀 Server running on http://localhost:${PORT}`);
});

STEP 7: สร้าง 5-Route CRUD Router (routes/studentRoutes.js)

POST(201), GET(200), GET/:id, PUT({new:true, runValidators:true}), DELETE

⏱️ ~5 นาที
ไฟล์: routes/studentRoutes.js 
const express = require('express');
const router = express.Router();
const Student = require('../models/Student');

// 1. CREATE: POST /api/students
router.post('/', async (req, res) => {
  try {
    const student = await Student.create(req.body);
    res.status(201).json(student);
  } catch (err) {
    if (err.code === 11000) {
      return res.status(400).json({ error: 'Duplicate studentId error' });
    }
    res.status(400).json({ error: err.message });
  }
});

// 2. READ ALL: GET /api/students (รองรับ Query Filter)
router.get('/', async (req, res) => {
  try {
    const filter = {};
    if (req.query.major) filter.major = req.query.major;
    if (req.query.isActive !== undefined) filter.isActive = req.query.isActive === 'true';

    const students = await Student.find(filter).sort({ createdAt: -1 });
    res.status(200).json(students);
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

// 3. READ ONE BY ID: GET /api/students/:id
router.get('/:id', async (req, res) => {
  try {
    const student = await Student.findById(req.params.id);
    if (!student) {
      return res.status(404).json({ message: 'Student not found' });
    }
    res.status(200).json(student);
  } catch (err) {
    res.status(400).json({ error: 'Invalid ID format or Error: ' + err.message });
  }
});

// 4. UPDATE: PUT /api/students/:id (สำคัญมาก: ต้องมี { new: true, runValidators: true })
router.put('/:id', async (req, res) => {
  try {
    const updatedStudent = await Student.findByIdAndUpdate(
      req.params.id,
      req.body,
      { new: true, runValidators: true }
    );
    if (!updatedStudent) {
      return res.status(404).json({ message: 'Student not found' });
    }
    res.status(200).json(updatedStudent);
  } catch (err) {
    res.status(400).json({ error: err.message });
  }
});

// 5. DELETE: DELETE /api/students/:id
router.delete('/:id', async (req, res) => {
  try {
    const deletedStudent = await Student.findByIdAndDelete(req.params.id);
    if (!deletedStudent) {
      return res.status(404).json({ message: 'Student not found' });
    }
    res.status(200).json({ message: 'Student deleted successfully', id: req.params.id });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

module.exports = router;

app.delete('/api/users/:email', async (req, res) => {
  try {
    const [result] = await pool.query(
      'UPDATE users SET deleted_at = NOW() WHERE email = ? AND deleted_at IS NULL',
      [req.params.email]
    );
    if (result.affectedRows === 0) return res.status(404).json({ error: 'User not found' });
    res.status(200).json({ message: 'Soft-deleted successfully' });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

7. Mongoose Schema & 5-Route CRUD Handlers 

const mongoose = require('mongoose');

// Schema
const studentSchema = new mongoose.Schema({
  studentId: { type: String, required: true, unique: true, trim: true },
  name: { type: String, required: true, trim: true },
  gpa: { type: Number, min: 0.0, max: 4.0, default: 0.0 },
  isActive: { type: Boolean, default: true }
}, { timestamps: true });
const Student = mongoose.model('Student', studentSchema);

// 1. POST Create
router.post('/', async (req, res) => {
  try {
    const doc = await Student.create(req.body);
    res.status(201).json(doc);
  } catch (err) {
    if (err.code === 11000) return res.status(400).json({ error: 'Duplicate studentId' });
    res.status(400).json({ error: err.message });
  }
});

// 2. GET Read All
router.get('/', async (req, res) => {
  const list = await Student.find().sort({ createdAt: -1 });
  res.status(200).json(list);
});

// 3. GET Read One
router.get('/:id', async (req, res) => {
  const doc = await Student.findById(req.params.id);
  if (!doc) return res.status(404).json({ message: 'Not found' });
  res.status(200).json(doc);
});

// 4. PUT Update ({ new: true, runValidators: true })
router.put('/:id', async (req, res) => {
  const doc = await Student.findByIdAndUpdate(req.params.id, req.body, { new: true, runValidators: true });
  if (!doc) return res.status(404).json({ message: 'Not found' });
  res.status(200).json(doc);
});

// 5. DELETE Delete
router.delete('/:id', async (req, res) => {
  const doc = await Student.findByIdAndDelete(req.params.id);
  if (!doc) return res.status(404).json({ message: 'Not found' });
  res.status(200).json({ message: 'Deleted', id: req.params.id });
});

Day 01: Introduction to Server-Side Web Development, HTTP & Rendering Models

Day 01 • 03/07/2026

1. Client-Server 3-Tier Architecture & Web Evolution

วิวัฒนาการของการพัฒนาเว็บแบ่งออกเป็น 3 ยุคหลัก: Web 1.0 (Static Web) ➔ เซิร์ฟเวอร์ส่งไฟล์ HTML/CSS นิ่งๆ ให้เบราว์เซอร์แสดงผลอย่างเดียว, Web 2.0 (Dynamic & Interactive Web) ➔ เกิดการรับส่งข้อมูลผ่าน AJAX/REST API ผู้ใช้สามารถสร้าง Content (User-Generated Content) และโต้ตอบแบบเรียลไทม์, Web 3.0 (Decentralized & Intelligent Web) ➔ บล็อกเชน, AI-driven backend, Edge computing.

// 3-Tier Web Architecture Flow:

[Client / Browser] ──── HTTP Request (JSON/Form) ────► [Express Application Server]

[Express Application Server] ──── SQL / MQL Query ────► [Database: MySQL / MongoDB]

[Express Application Server] ◄─── Result Sets / Documents ─── [Database: MySQL / MongoDB]

[Client / Browser] ◄─── HTTP Response (JSON / Status Code) ─── [Express Application Server]

2. เปรียบเทียบ SSR vs CSR vs SSG vs ISR

คุณสมบัติ SSR (Server-Side) CSR (Client-Side) SSG (Static Gen)
จุดเรนเดอร์ HTML เซิร์ฟเวอร์ทุก Request เบราว์เซอร์ผ่าน JS Bundle Build Time ตอน Deploy
SEO & Social Bots 100% Perfect ปานกลาง/ต่ำ (Bot ไม่รอ JS) 100% Perfect
First Contentful Paint (FCP) เร็วมาก ช้า (รอโหลด JS Bundle) เร็วที่สุดในโลก (CDN Cache)
ความสดใหม่ของข้อมูล เรียลไทม์ 100% เรียลไทม์ผ่าน API ต้อง Re-build ใหม่เมื่อข้อมูลเปลี่ยน

3. HTTP Master Status Codes & RESTful Constraints

2xx Success
  • 200 OK: คำขอสำเร็จ (GET/PUT/DELETE)
  • 201 Created: สร้าง Resource ใหม่สำเร็จ (POST)
  • 204 No Content: สำเร็จแต่ไม่มี Body ส่งกลับ
4xx Client Errors
  • 400 Bad Request: ข้อมูลไม่ถูกต้อง/ซ้ำ (11000)
  • 401 Unauthorized: ไม่ได้ล็อกอิน / ไม่มี Token
  • 403 Forbidden: ไม่มีสิทธิ์เข้าถึง
  • 404 Not Found: ไม่พบ URL หรือ Record ID
5xx Server Errors
  • 500 Internal Server Error: Unhandled Exception
  • 502 Bad Gateway: เกตเวย์รับคำตอบผิดพลาด
  • 503 Service Unavailable: เซิร์ฟเวอร์ล่ม/รับโหลดไม่ไหว
⚡ Idempotent Methods:

• Safe & Idempotent (ยิงกี่ครั้งสถานะเซิร์ฟเวอร์ไม่เปลี่ยน): GET, HEAD, OPTIONS

• Idempotent (ยิงกี่ครั้งผลลัพธ์สุดท้ายเหมือนเดิม): PUT (แทนที่ทั้งหมด), DELETE (ลบครั้งเดียวกับหลายครั้งสถานะสุดท้ายคือไม่มี)

• Non-Idempotent (ยิงซ้ำสร้างข้อมูลใหม่ซ้ำซ้อน): POST (สร้าง Resource ใหม่ทุกครั้งที่ยิง)

Day 02: Git Version Control, Branching Strategy & Merge Conflict Resolution

Day 02 • 29/06/2026

1. สถาปัตยกรรม 4 สถานะของ Git (The 4 Git States)

1. Working Directory: พื้นที่ทำงาน ไฟล์จริงในโฟลเดอร์ที่ถูกสร้างหรือแก้ไข

2. Staging Area (Index): ตะกร้าพักไฟล์ที่เตรียมจะบันทึก (เกิดจากการรัน git add <file> หรือ git add .)

3. Local Repository (HEAD): ฐานข้อมูลประวัติการแก้ไขในเครื่อง (เกิดจากการรัน git commit -m "msg")

4. Remote Repository (Origin): เซิร์ฟเวอร์กลางบนคลาวด์ เช่น GitHub/GitLab (เกิดจากการรัน git push origin <branch>)

2. คำสั่ง Git สำคัญที่ต้องใช้ในห้องสอบ

git init ➔ เริ่มต้นสร้าง Git Repo ในโฟลเดอร์

git branch -M main ➔ เปลี่ยนชื่อ Master Branch เป็น main

git status ➔ ตรวจสอบสถานะไฟล์ (Untracked, Modified, Staged)

git add . ➔ นำไฟล์ทั้งหมดเข้าสู่ Staging Area

git commit -m "feat: init" ➔ บันทึก Snapshot ลง Local Repo

git remote add origin <URL> ➔ ผูก Remote GitHub Repo

git push -u origin main ➔ อัปโหลดโค้ดขึ้น GitHub

3. คู่มือแก้ปัญหา Merge Conflict Step-by-Step

// ตัวอย่างโครงสร้าง Conflict ในไฟล์โค้ดเมื่อรัน git merge:

<<<<<<< HEAD (โค้ดของ Branch ปัจจุบัน เช่น main)

const PORT = process.env.PORT || 5000;

=======

const PORT = process.env.APP_PORT || 8080;

>>>>>>> feature/custom-port (โค้ดของ Branch ที่ต้องการนำมา Merge)

🛠️ 3 ขั้นตอนการแก้:

1. เปิดไฟล์ใน VS Code ➔ ลบเครื่องหมาย <<<<<<< HEAD, =======, และ >>>>>>> branch ทิ้ง

2. ตัดสินใจเลือกโค้ดเวอร์ชันที่ถูกต้อง (หรือรวมโค้ดทั้งสองฝั่งเข้าด้วยกัน)

3. สั่งบันทึกและรัน: git add <file> && git commit -m "fix: resolve merge conflict"

Day 02: Docker Containerization, Layer Caching & Docker Compose

Day 02 • 29/06/2026

1. กลไกภายในของ Linux Kernel: Namespaces & cgroups

  • Namespaces (Isolation): แยกมุมมองของ Process ไม่ให้มองเห็นกัน ประกอบด้วย:
    • • PID: แยก Process ID (PID 1 ในคอนเทนเนอร์เป็นอิสระ)
    • • NET: แยก Network Interfaces, IP Table, Routing
    • • MNT: แยก Filesystem Mount points
    • • IPC: แยก Inter-Process Communication & Shared Memory
    • • UTS: แยก Hostname & Domain Name
    • • USER: แมป User UID/GID ภายในกับภายนอก
  • Control Groups (cgroups): กำหนดขีดจำกัดการใช้งานทรัพยากร (Resource Throttling) เช่น กำหนดให้ใช้ RAM สูงสุด 512MB, CPU 0.5 core
  • Union Filesystem (Overlay2): ชั้นของ Image Layer ซ้อนกันแบบ Read-Only และมี Container Layer ด้านบนสุดเป็น Read-Write

1. Master SQL Joins Comparison Matrix

INNER JOIN: ดึงเฉพาะข้อมูลที่มีคู่ตรงกันทั้ง 2 ตาราง

SELECT * FROM students s INNER JOIN enrollments e ON s.id = e.student_id;

LEFT JOIN: ดึงตารางซ้ายทั้งหมด + ตารางขวาที่ตรงกัน (ถ้าไม่ตรงเป็น NULL)

SELECT s.name, e.course_name FROM students s LEFT JOIN enrollments e ON s.id = e.student_id;

FULL OUTER JOIN (MySQL Union):

SELECT * FROM t1 LEFT JOIN t2 ON t1.id = t2.id UNION SELECT * FROM t1 RIGHT JOIN t2 ON t1.id = t2.id;
