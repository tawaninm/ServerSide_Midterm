1. Intro to Server-Side & HTTP Architecture

Day 01
  • Client-Server & 3-Tier Architecture: Client (Presentation / UI) ⇄ Application Server (Business Logic, Validation, Authentication) ⇄ Database (Data Storage & Persistence).
  • Rendering Models เปรียบเทียบเจาะลึก:

    SSR (Server-Side): Render HTML บน Server ➔ ส่ง HTML สำเร็จรูปให้ Browser ➔ Fast First Paint & Best for SEO.

    CSR (Client-Side): Server ส่ง HTML เปล่า + JS Bundle ➔ Browser ทำการ Render DOM ➔ High Interactivity (SPA) แต่ Initial Load ช้ากว่า.

    SSG (Static Site): Build HTML ล่วงหน้าตอน Compile Time ➔ เสิร์ฟผ่าน CDN รวดเร็วระดับเสี้ยววินาที.
  • HTTP Protocol & RESTful API: Stateless Protocol • HTTP Methods: GET (Read / Idempotent), POST (Create - Status 201), PUT (Replace all fields), PATCH (Partial update), DELETE (Remove - 200/204).
  • HTTP Status Codes: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthorized (No Token), 403 Forbidden (No Permission), 404 Not Found, 409 Conflict, 500 Internal Server Error.

2. Git Architecture & Version Control Systems

Day 02 • Git
  • 4 Git Architecture States: Working Directory ➔ git add ➔ Staging Area (Index) ➔ git commit ➔ Local Repository ➔ git push ➔ Remote Repository.
  • Branching & Fast-Forward vs 3-Way Merge: git checkout -b feature/login (หรือ git switch -c feature/login) • เมื่อรวมโค้ด git merge feature/login หากไม่มี commit แทรกจะเป็น Fast-Forward, หากมีจะเกิด 3-Way Merge.
  • Merge Conflicts Resolution (กฎ 3 สัญลักษณ์): เมื่อเกิดชนกัน Git จะทำเครื่องหมาย <<<<<<< HEAD (โค้ดเรา), ======= (ตัวแบ่ง), >>>>>>> branch (โค้ดที่ดึงมา) ➔ แก้ไขไฟล์ ➔ ลบเครื่องหมาย ➔ git add . ➔ git commit.
  • Undoing & Stash: git restore <file> (ยกเลิกใน working dir), git restore --staged <file> (unstage), git reset --soft HEAD~1 (ย้อน commit เก็บ stage), git stash save & git stash pop (พักงานชั่วคราว).
  • GitHub Remote Repo: เชื่อมต่อและผลักดันโค้ดขึ้น GitHub ด้วย git remote add origin https://github.com/tawaninm/ServerSide_Midterm.git และ git push -u origin main.

3. Docker Containerization & Layer Caching

Day 02 • Docker
  • VM vs Docker: VM จำลอง Hardware ทั้งระบบ มี Hypervisor + Full Guest OS (หนัก/ช้า/กินแรม GB) vs Docker ใช้ Linux Kernel Namespaces & cgroups แชร์ OS Host (เบา/เร็วระดับมิลลิวินาที/ขนาด MB).
  • Dockerfile Layer Caching Best Practice: วาง COPY package*.json ./ และ RUN npm install ไว้ก่อน COPY . . เพื่อให้ Docker ทำ Cache Layer หากโค้ดเปลี่ยนแต่ dependencies ไม่เปลี่ยน ไม่ต้องโหลด node_modules ซ้ำ.
  • Docker Compose Orchestration: จัดการ Multi-Container ด้วย docker-compose.yaml กำหนด services (web, mysql, mongo), ports binding, volumes persistent data, และ environment variables.
  • Core Docker Commands: docker build -t app:v1 ., docker run -d -p 5000:5000 --name web app:v1, docker ps -a, docker logs -f web, docker exec -it web sh, docker compose up -d, docker compose down -v.

4. Node.js Internals, libuv & Core Modules

Day 04
  • Node.js Architecture: V8 JavaScript Engine + libuv (Event Loop & Thread Pool 4 workers) Single-Threaded Non-blocking I/O รองรับ Concurrent Requests มหาศาล.
  • Asynchronous Evolution: Callback Hell (Pyramid of Doom) ➔ Promise (.then().catch()) ➔ Async/Await with try/catch (อ่านง่ายเหมือน Synchronous Code).
  • Essential Core Modules:
    • fs / fs.promises: readFile, writeFile, appendFile, unlink, mkdir
    • path: join(__dirname, 'public'), resolve, extname, basename
    • http: createServer((req, res) => {...}), parse headers & URL
    • events: EventEmitter, on('event', fn), emit('event', data)
    • os & process: os.cpus(), process.env, process.exit(), process.cwd()
  • Module Systems & SemVer: CommonJS (require/module.exports) vs ES Modules (import/export) • Semantic Versioning: ^1.2.3 (Minor/Patch auto-update) vs ~1.2.3 (Patch only).

5. Express.js & 5 Middleware Types Architecture

Day 06
  • Middleware Mechanism: Function ที่ทำงานระหว่าง Request และ Response ((req, res, next) => {...}) • กฎเหล็ก: ต้องเรียก next() หรือส่ง response (res.json()) เสมอ มิฉะนั้น Request จะค้าง (Hanging Request) จน Timeout.
  • 5 Middleware Categories:

    1. Application-level: app.use(logger) ทำงานทุก Request

    2. Router-level: router.use(authCheck) ผูกกับเฉพาะ Router

    3. Built-in: express.json() แปลง JSON Body, express.static()

    4. Third-party: cors(), morgan(), helmet()

    5. Error-handling: (err, req, res, next) ต้องมี 4 พารามิเตอร์เสมอ และวางไว้ล่างสุดของแอป
  • 12-Factor App & dotenv: แยก Configuration ออกจาก Code ด้วย require('dotenv').config() และไฟล์ .env (ห้าม Push ขึ้น Git) + .env.example (Push เป็นตัวอย่าง).

6. MySQL2 Connection Pool & Soft Delete Pattern

Day 06 • MySQL
  • Connection Pooling (`mysql2/promise`): ใช้ mysql.createPool({...}) เพื่อ Reuse Database Connections แทนการเปิด/ปิดใหม่ทุก Request เพิ่มประสิทธิภาพและความเสถียรของระบบ.
  • Prepared Statements & Anti-SQL Injection: ใช้ pool.execute('SELECT * FROM users WHERE id = ?', [id]) ส่ง Parameter ผ่าน Placeholder ? เสมอ ห้ามนำ String มาต่อกันตรงๆ.
  • Soft Delete vs Hard Delete:

    แทนที่จะลบถาวรด้วย DELETE FROM ให้ใช้ Soft Delete: UPDATE users SET is_deleted = 1, deleted_at = NOW() WHERE id = ? เพื่อรักษา Audit Trail, Referential Integrity และกู้คืนข้อมูลได้.
  • Transactions ACID: const conn = await pool.getConnection(); await conn.beginTransaction(); ... await conn.commit(); conn.release(); ป้องกันข้อมูลไม่สมบูรณ์เมื่อเกิด Error.

7. MongoDB Mongoose ODM 5-Route CRUD & E11000 Error

Day 06 • Mongo
  • Mongoose Schema & Validation: กำหนด Schema Types (String, Number, Boolean, Date, ObjectId) พร้อม Validators (required, unique, min, max, enum, match, custom validate).
  • MongoDB E11000 Duplicate Key Error: เมื่อ unique: true ชนกัน MongoDB Driver จะโยนรหัสข้อผิดพลาด code 11000 (ไม่ใช่ Mongoose ValidationError ปกติ) ➔ ต้องดักจับใน Error Middleware: if (err.code === 11000) res.status(400).json({ error: 'Duplicate field value' }).
  • Complete 5-Route RESTful Controller:

    1. GET /api/users ➔ await User.find()

    2. GET /api/users/:id ➔ await User.findById(id) (ตรวจ ObjectId.isValid)

    3. POST /api/users ➔ await User.create(req.body) (Status 201)

    4. PUT /api/users/:id ➔ await User.findByIdAndUpdate(id, req.body, { new: true, runValidators: true })

    5. DELETE /api/users/:id ➔ await User.findByIdAndDelete(id)

8. MongoDB Atlas M0 Cloud Cluster Setup & Security

Day 06 • Atlas
  • M0 Free Tier Cluster Creation: สร้าง Cluster บน AWS/GCP/Azure ➔ เลือก Provider & Region ที่ใกล้ที่สุด (เช่น Singapore / ap-southeast-1) เพื่อ Latency ต่ำสุด.
  • Security & User Authentication: สร้าง Database User (Username & Password) พร้อมสิทธิ์ readWriteAnyDatabase (ห้ามใช้เครื่องหมาย @ หรือ : ใน password หรือต้อง URL Encode).
  • Network Access & IP Whitelisting: ไปที่เมนู Network Access ➔ เพิ่ม IP Address ➔ เลือก Allow Access from Anywhere (0.0.0.0/0) สำหรับงานพัฒนาและห้องสอบ เพื่อป้องกัน Connection Refused.
  • Standard SRV Connection String: mongodb+srv://<username>:<password>@cluster0.abcde.mongodb.net/exam_db?retryWrites=true&w=majority

9. Advanced SQL Architecture, 5 Joins, Constraints & Prisma ORM

Day 07 • SQL & Prisma
4 Sublanguages of SQL:

DDL: CREATE, ALTER, DROP, TRUNCATE • DML: INSERT, UPDATE, DELETE, SELECT • DCL: GRANT, REVOKE • TCL: COMMIT, ROLLBACK, SAVEPOINT.

DROP vs TRUNCATE vs DELETE:

• DELETE (DML): ลบทีละแถว, มี WHERE, ช้าสุด, Rollback ได้, Triggers ทำงาน

• TRUNCATE (DDL): ลบข้อมูลทั้งหมด, Reset Auto-increment เป็น 1, เร็วมาก

• DROP (DDL): ลบทั้งโครงสร้างและข้อมูลของตารางทิ้งอย่างถาวร

GROUP BY vs HAVING:

WHERE กรองระดับแถว ก่อน รวมกลุ่ม (ห้ามใช้ Aggregate ใน WHERE) vs HAVING กรองระดับกลุ่ม หลัง คำนวณ Aggregate Function แล้ว (เช่น HAVING COUNT(*) > 5).

Relational Joins & Subqueries:

INNER JOIN (จุดตัดร่วม), LEFT JOIN (ซ้ายทั้งหมด + ขวาที่ตรง), RIGHT JOIN (ขวาทั้งหมด + ซ้ายที่ตรง), FULL OUTER JOIN (จำลองด้วย LEFT UNION RIGHT), SELF JOIN (ลำดับขั้นพนักงานและหัวหน้า), EXISTS (ประสิทธิภาพสูงใน Correlated Subquery).

Integrity Constraints & Views:

PRIMARY KEY, FOREIGN KEY (ON DELETE CASCADE / SET NULL), UNIQUE, NOT NULL, CHECK, DEFAULT • สร้างตารางเสมือนด้วย CREATE VIEW view_name AS SELECT ...

Prisma Modern Type-Safe ORM:

กำหนดโมเดลใน schema.prisma ➔ รัน npx prisma migrate dev ➔ ใช้งานใน Express ผ่าน prisma.user.findMany(), prisma.user.create(), prisma.user.update(), prisma.user.delete() หรือ Raw SQL prisma.$queryRaw.

  });
});

app.listen(PORT, () => {

});

STEP 7: สร้าง 5-Route CRUD Router (routes/studentRoutes.js)

POST(201), GET(200), GET/:id, PUT({new:true, runValidators:true}), DELETE

⏱️ ~5 นาที
ไฟล์: routes/studentRoutes.js 
const express = require('express');
const router = express.Router();
const Student = require('../models/Student');

// 1. CREATE: POST /api/students
router.post('/', async (req, res) => {
  try {
    const student = await Student.create(req.body);
    res.status(201).json(student);
  } catch (err) {
    if (err.code === 11000) {
      return res.status(400).json({ error: 'Duplicate studentId error' });
    }
    res.status(400).json({ error: err.message });
  }
});

// 2. READ ALL: GET /api/students (รองรับ Query Filter)
router.get('/', async (req, res) => {
  try {
    const filter = {};
    if (req.query.major) filter.major = req.query.major;
    if (req.query.isActive !== undefined) filter.isActive = req.query.isActive === 'true';

    const students = await Student.find(filter).sort({ createdAt: -1 });
    res.status(200).json(students);
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

// 3. READ ONE BY ID: GET /api/students/:id
router.get('/:id', async (req, res) => {
  try {
    const student = await Student.findById(req.params.id);
    if (!student) {
      return res.status(404).json({ message: 'Student not found' });
    }
    res.status(200).json(student);
  } catch (err) {
    res.status(400).json({ error: 'Invalid ID format or Error: ' + err.message });
  }
});

// 4. UPDATE: PUT /api/students/:id (สำคัญมาก: ต้องมี { new: true, runValidators: true })
router.put('/:id', async (req, res) => {
  try {
    const updatedStudent = await Student.findByIdAndUpdate(
      req.params.id,
      req.body,
      { new: true, runValidators: true }
    );
    if (!updatedStudent) {
      return res.status(404).json({ message: 'Student not found' });
    }
    res.status(200).json(updatedStudent);
  } catch (err) {
    res.status(400).json({ error: err.message });
  }
});

// 5. DELETE: DELETE /api/students/:id
router.delete('/:id', async (req, res) => {
  try {
    const deletedStudent = await Student.findByIdAndDelete(req.params.id);
    if (!deletedStudent) {
      return res.status(404).json({ message: 'Student not found' });
    }
    res.status(200).json({ message: 'Student deleted successfully', id: req.params.id });
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

module.exports = router;

1. สถาปัตยกรรม Client-Server และ 3-Tier Architecture

สถาปัตยกรรม Client-Server เป็นรากฐานของเว็บ โดยแบ่งบทบาทออกเป็นสองฝั่งชัดเจน:

  • Client (Frontend / Presentation Layer): ทำหน้าที่รับ User Input และแสดงผล User Interface ผ่าน HTML, CSS, JavaScript บน Web Browser หรือ Mobile App
  • Server (Backend / Application Layer): ศูนย์กลางการประมวลผล Business Logic, ทำการตรวจสอบสิทธิ์ (Authentication & Authorization), คำนวณข้อมูล และสื่อสารกับ Data Storage
  • Database (Data Tier): แหล่งจัดเก็บและรักษาความคงอยู่ของข้อมูล (Data Persistence) เช่น MySQL, PostgreSQL, MongoDB

2. เปรียบเทียบรูปแบบการแสดงผลเว็บไซต์ (Rendering Models)

คุณสมบัติ (Criteria) Server-Side Rendering (SSR) Client-Side Rendering (CSR) Static Site Generation (SSG)
สถานที่ Render Render บน Server ทุก Request Render บน Browser (Client JS) Render ตอน Build Time (ล่วงหน้า)
First Contentful Paint (FCP) เร็วมาก (ได้ HTML พร้อมแสดงผลทันที) ช้ากว่า (ต้องรอโหลด JS Bundle จนเสร็จ) เร็วที่สุด (เสิร์ฟไฟล์ตรงจาก CDN)
Search Engine Optimization (SEO) ยอดเยี่ยม (Web Crawler อ่านเนื้อหาได้ทันที) ปานกลาง/ต้องพึ่ง Dynamic Rendering ยอดเยี่ยม
Server Resource Load สูง (Server ต้องคำนวณและสร้างหน้าใหม่) ต่ำมาก (Server เสิร์ฟแค่ JSON API & Static JS) ต่ำมากที่สุด

3. HTTP Protocol, RESTful API & Status Codes

HTTP (Hypertext Transfer Protocol) เป็น Stateless Protocol หมายความว่าแต่ละ Request จะทำงานเป็นอิสระต่อกัน Server จะไม่จำ State ของ Client เว้นแต่จะใช้ Cookie, Session หรือ JWT Token ในการยืนยันตัวตน.

HTTP Methods & Idempotency:

• GET: ดึงข้อมูล (Idempotent - เรียกซ้ำผลลัพธ์เหมือนเดิม)

• POST: สร้างข้อมูลใหม่ (Non-Idempotent - Status 201 Created)

• PUT: อัปเดตข้อมูลทั้งก้อน (Replace All Fields)

• PATCH: อัปเดตเฉพาะบางฟิลด์ (Partial Update)

• DELETE: ลบข้อมูล (Idempotent - Status 200/204)

Standard Status Codes:

• 200 OK: คำขอสำเร็จและส่งข้อมูลกลับ

• 201 Created: สร้างทรัพยากรใหม่สำเร็จ (POST)

• 400 Bad Request: ข้อมูลที่ส่งมาไม่ถูกต้อง (Validation Fail)

• 401 Unauthorized: ขาด Token หรือ Credential ไม่ถูกต้อง

• 404 Not Found: ไม่พบ URL หรือ Resource ที่ระบุ

• 500 Internal Server Error: เกิดข้อผิดพลาดฝั่ง Server

1. Virtual Machine vs Docker Container Architecture

Docker แก้ปัญหาคลาสสิก "It works on my machine" โดยการ Bundle โค้ด, รันไทม์, System Libraries และ Dependencies ทั้งหมดให้อยู่ใน Container เดียวกัน:

Virtual Machine (VM):

ใช้ Hypervisor (Type 1 หรือ Type 2) จำลอง Virtual Hardware และต้องติดตั้ง Full Guest OS ทุกตัว ส่งผลให้กินพื้นที่ Disk ระดับ GB, ใช้เวลาบูตเป็นนาที และกิน RAM/CPU Overhead มหาศาล

Docker Container:

ทำงานผ่าน Docker Engine แชร์ Linux Host Kernel ร่วมกัน อาศัยกลไก Namespaces (PID, NET, MNT, IPC, UTS) ในการแยกสิทธิ์ และ cgroups ในการจำกัด Resource ทำให้บูตได้ในระดับมิลลิวินาทีและมีขนาดเพียงหลัก MB

1. สถาปัตยกรรมภายในของ Node.js (V8 + libuv Event Loop)

Node.js เป็น JavaScript Runtime ที่ทำงานบน V8 Engine และใช้ libuv C++ Library ในการจัดการ Event Loop และ Worker Thread Pool (ค่าเริ่มต้น 4 Threads):

  • Single-Threaded Event Loop: รันโค้ด JavaScript ใน Main Thread เดียว ทำให้ไม่ต้องกังวลเรื่อง Thread Deadlock
  • Non-blocking I/O: เมื่อมีการอ่านไฟล์หรือเรียก Database ตัว Node.js จะส่งต่องานให้ OS Kernel หรือ libuv Worker Threads จัดการในพื้นหลัง และแจ้งเตือนผ่าน Callback/Promise เมื่อข้อมูลพร้อม

2. MySQL2 Connection Pool, Prepared Statements และ Soft Delete

// 1. สร้าง Connection Pool

const mysql = require('mysql2/promise');

const pool = mysql.createPool({ host: 'localhost', user: 'root', password: 'password', database: 'exam_db', connectionLimit: 10 });

// 2. Prepared Query (ป้องกัน SQL Injection 100%)

const [rows] = await pool.execute('SELECT * FROM users WHERE id = ? AND is_deleted = 0', [userId]);

// 3. การทำ Soft Delete (ไม่ใช้ DELETE FROM จริง)

await pool.execute('UPDATE users SET is_deleted = 1, deleted_at = NOW() WHERE id = ?', [userId]);

1. สถาปัตยกรรมภาษา SQL (4 Sublanguages)

1. DDL (Data Definition Language)

จัดการโครงสร้าง Schema ของฐานข้อมูล

คำสั่ง: CREATE, ALTER, DROP, TRUNCATE

2. DML (Data Manipulation Language)

จัดการข้อมูลภายในตาราง (CRUD)

คำสั่ง: INSERT, UPDATE, DELETE, SELECT

3. DCL (Data Control Language)

ควบคุมสิทธิ์และความปลอดภัยของผู้ใช้

คำสั่ง: GRANT, REVOKE

4. TCL (Transaction Control Language)

ควบคุมธุรกรรมข้อมูลตามหลัก ACID

คำสั่ง: COMMIT, ROLLBACK, SAVEPOINT

2. ตารางเปรียบเทียบเจาะลึก: DROP TABLE vs TRUNCATE TABLE vs DELETE FROM

เกณฑ์เปรียบเทียบ DROP TABLE TRUNCATE TABLE DELETE FROM
ประเภทคำสั่ง DDL DDL DML
สิ่งที่ถูกลบ โครงสร้างตาราง + ข้อมูลทั้งหมด ข้อมูลทั้งหมด (โครงสร้างยังคงอยู่) ข้อมูลตามเงื่อนไข WHERE
การ Rollback ใน Transaction ไม่ได้ (Auto-commit) ไม่ได้ (ใน MySQL ส่วนใหญ่) ได้ (Rollback สมบูรณ์)
การรีเซ็ต Auto-increment ตารางหายไป รีเซ็ตกลับเป็น 1 ทันที ไม่รีเซ็ต (นับต่อจากค่าเดิม)
ความเร็วในการทำงาน เร็วมาก เร็วมาก (Deallocate Pages) ช้าที่สุด (ลบทีละ Record + Log)

3. Relational Joins ทั้ง 5 รูปแบบ

1. INNER JOIN (Intersection)

ดึงเฉพาะแถวที่มี Key ตรงกันทั้งสองตาราง

SELECT * FROM users u INNER JOIN orders o ON u.id = o.user_id;

2. LEFT (OUTER) JOIN

ดึงแถวทั้งหมดจากตารางซ้าย หากตารางขวาไม่ตรงจะใส่ NULL

SELECT * FROM users u LEFT JOIN orders o ON u.id = o.user_id;

3. FULL OUTER JOIN ใน MySQL

MySQL ไม่รองรับ FULL JOIN ตรงๆ ต้องจำลองด้วย UNION:

SELECT * FROM A LEFT JOIN B ON A.id = B.id UNION SELECT * FROM A RIGHT JOIN B ON A.id = B.id;

4. SELF JOIN (ลำดับขั้น)

Join ตารางเดิมเข้ากับตัวเอง เพื่อหาหัวหน้างาน:

SELECT e.name, m.name AS manager FROM emp e LEFT JOIN emp m ON e.mgr_id = m.id;
